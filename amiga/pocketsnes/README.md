# PocketSNES A9 diagnostic

Separate, headless SNES-core experiment for the A4000TX / ZZ9000. It does not
replace ZZSnes-Mesen or provide a game launcher. No ROM is supplied except our
original 32 KiB checkerboard fixture, generated by
`scripts/build_mesen_snes_system.py`.

## Core choice

The tested source is [libretro/snes9x2002](https://github.com/libretro/snes9x2002),
formerly PocketSNES, pinned to `6ffbf9ef4f0063e1f1b78a40d10c50fc52f2524c`.
The older ARMSNES-libretro and DrPocketSNES references have handheld-specific
assembly renderers. This first comparison uses Snes9x2002's portable C CPU,
PPU, SPC700 and DSP path (`__OLD_RASTER_FX__`), compiled for Cortex-A9 ARM mode.
It is not a measurement of DrPocketSNES's assembly CPU or renderer.

All upstream copyright/license headers are preserved in the generated source.
Snes9x/PocketSNES has a noncommercial license; it is not Mesen's GPL-3.0 core.
No emulator code was copied into Mesen. Bare-metal runtime and XACP launch
scaffolding are shared with the existing local diagnostics.

## Test contract

- Same original ordinary-LoROM Mode 0 checkerboard as the Mesen diagnostic.
- Six startup frames, CPU/bus/DMA/PPU plus SPC700/DSP and silent PCM output.
- No frame skipping, idle shutdown, game-specific speed hacks or sound mute.
  Transparency, interpolation, echo emulation and the normal 32,040 Hz audio mixer stay on.
  The SPC700 boot-ROM AA/BB handshake is checked too.
- No Workbench drawing, framebuffer transfer, audible playback or external ROM
  loading. Frame times are core work, not demonstrated game/display FPS.
- Video oracle: 256x224 red/green checkerboard from frame two onward. PocketSNES
  crops overscan and uses green `0x07c0` in RGB565; Mesen returns a 256x239 image
  in SNES colour encoding. Compare visible content, not cross-core raw hashes.
- Six-frame native reference: video `67711dc5`, silent PCM `77d82d05`, 3,208
  stereo samples. Mesen's six-frame startup produces 3,119 samples; the cores'
  initial frame boundaries and audio rates differ. A timing ratio is not cycle-equivalent work.
- Pixel hashing/verification happens after the measured `retro_run()` interval;
  audio hashing is inside its callback. Initialisation/ROM load/deinit are outside
  the timer. One warm-up and ten samples are requested on the board.

Two header-size expressions in upstream ROM identification have undefined
negative/oversized shifts for small/headerless images. The generated patch
replaces the score comparison with a range comparison and bounds the size label.
The fixture remains byte-identical to Mesen's. Generated `integration.patch`
and `upstream.json` record adaptations and original file hashes.

## Memory and lifecycle

Exec owns the entire 24 MiB allocation. The runtime mapping probe derives the
ARM view; there are no fixed board-RAM allocations. Image <1 MiB; tables at
+0x100000..0x110000, witness +0x120000, uncached mailbox
+0x180000..0x184000, zeroed BSS +0x220000, final 192 KiB reserved for stack.
The 18 MiB bounded heap serves the upstream buffers (including its full ROM and
main/subscreen reservations). These are offsets within the owned allocation.

Generated copies of the established MMU helper change offsets only. Private
inner WB/WA, outer noncacheable, noncacheable mailbox, execute-never data,
read-only timer page, single-Core1 ownership and firmware state restoration
retain the existing contracts. The host enforces deadlines, active cancellation,
RET1, register/cache witness and synchronous reset before freeing memory.

## Local builds

This workbench currently supplies the existing `zzffmpeg-toolchain` Podman
container (GCC arm-none-eabi 15.3, picolibc 1.8.12) and picolibc sources under
`.context/amiga/ffmpeg-bench/`. Generated tools/binaries remain in `.context/`.
This is an experimental local build, not a standalone SDK/release package.

```
python3 scripts/build_pocketsnes.py
python3 scripts/build_pocketsnes_libc.py
python3 scripts/build_pocketsnes_arm.py
python3 scripts/build_pocketsnes_host.py
.context/amiga/mesen-bench/venv/bin/python tests/amiga/pocketsnes/check_arm.py
make test-amiga-arm test-amiga
```

The libc preparation script rebuilds selected archive members as relocatable,
strict-alignment, soft-float C. The ELF packer refuses non-relative relocations,
constructors, unexpected loaded segments, escaped references and layout overlap.
Native ASan/UBSan runs establish reference results. ARM-model runs must verify
those results at two synthetic addresses, reject a corrupted palette, and
return promptly on cancellation before physical launch.

## Verified hardware result — 10 October 2026

On the physical ZZ9000 Cortex-A9 Core1, ten measured six-frame batches after
one warm-up averaged **4.6166 ms/frame** (range 4.6047–4.6297 ms).
The preceding Mesen word-memory diagnostic measured **39.945 ms/frame**.
This is about **8.65x** the fixture throughput, with the cross-core differences
above; it is not an accuracy-equivalent benchmark or a game-FPS claim.
The 16.67 ms budget for 60 Hz now looks plausible for simple content, but a
real game, active sound, input and presentation must be tested separately.

Native reference, relocated ARM model, physical pixels/PCM/SPC handshake,
active cancellation (134 ms), RET1, all 14 restored registers, MMU/cache witness
and memory release passed. No crash/reboot observed. Workbench, Roadie, bridge,
NES and Mesen apps remain running; existing executable hashes are unchanged.

Installed CLI: `SD032G:Dev/ZZSnes-Pocket/ZZSnes-Pocket-Bench`, 542,084 bytes,
MD5 `78a67d1434e85d6b304916333514e262`. Run with `Stack 65536`, redirecting its
output to a file. This diagnostic does not open a game screen. The verified
build is ARM mode, portable C, no VFP/NEON. The initial Thumb experiment was
rejected during model validation and was never launched on the Amiga.

Evidence: `amiga/records/2026-10-10/pocketsnes/`. The binary remains separate
from the Mesen and NES Workbench launchers. Preserved in the standalone ZZSNES-ARM-68K development backup.
